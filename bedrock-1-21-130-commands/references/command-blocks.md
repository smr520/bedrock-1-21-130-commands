# 命令方块：类型、链、延迟与排错

## 三种方块

| 类型 | 中文界面 | 什么时候跑 |
| --- | --- | --- |
| Impulse | 脉冲 | 每次收到红石信号跑一次 |
| Chain | 连锁 | 被前一个方块触发时跑 |
| Repeat | 循环 | 保持开启时每刻跑；有延迟时每 N 刻跑一次 |

拿方块：

```text
/give @s command_block
/give @s chain_command_block
/give @s repeating_command_block
```

## 两个开关

| 选项 | 值 | 作用 |
| --- | --- | --- |
| 条件 | 无条件 | 不管紧邻上游成功失败都执行当前块 |
| 条件 | 有条件 | 紧邻上游成功次数大于 0 才执行当前块 |
| 红石 | 需要红石 | 必须按钮/拉杆/压力板等供能 |
| 红石 | 保持开启 | 不需要红石，循环方块会一直跑 |

“有条件”判断的是**紧邻上游方块的成功次数**，不是分数条件。条件失败仍会把触发传给下一格，因此后续保护要写进命令：

```text
/execute if score @s coins matches 100.. run say 够了
```

## 链的方向

连锁方块靠箭头传递，箭头必须指下一格：

```text
[循环] → [连锁] → [连锁] → [连锁]
```

- 方块可以横着排、竖着排、拐弯排，但每一格的箭头都要对准下一格。
- 方向反了，链不会启动；拆掉重放比改方向快。
- 同一个 tick 内按链顺序执行。
- 链不能在同一 tick 里绕回自己；绕回去也只执行一次。

## 延迟与首刻

- 单位是游戏刻，20 tick ≈ 1 秒。
- 循环方块：延迟是“隔多久再跑一次”。
- 脉冲/连锁：延迟是“触发后等多久再跑”。
- 脉冲和循环方块的 `0` 与 `1` 在等待意义上等效；连锁方块的 `0` 是同 tick，`1` 是下一 tick。
- 循环方块的“首刻执行”（Execute on First Tick）只影响循环根；勾上会先跑一次再按延迟循环。
- 需要可取消、可显示或跨区块恢复的长延迟，优先使用记分板倒计时；短而固定的一次性延时可直接用方块延迟。

网易 1.21.130 的纯命令方块默认用“循环｜无条件｜保持开启｜延迟0”做高频根。红石驱动的重复触发受 C-tick 节拍影响，不应把它设计成稳定的 20 Hz 时钟；需要约 20 Hz 时使用保持开启的循环方块。

## 条件失败不会自动截断整条链

有条件方块判断的是它身后或上游方块的成功次数。条件不成立时，当前方块不执行，但触发仍会继续传给下一格；后面的无条件块仍可能运行。

因此：

- 条件门之后仍要运行的所有块，尤其是清理块，使用“无条件”。
- 需要“条件失败就停止后面动作”时，把完整条件写进每个后续 `execute if/unless ... run ...`，或拆成独立链。
- 不要依赖条件链制作多分支。分支默认写成彼此独立的 `execute if ... run ...`，需要互斥时再加一次性选择标记。
- 有条件块尽量保持直线，并紧邻它要检查的上游方块；拐弯后“身后”可能不是预想的那一格。

## 成功次数

有条件方块和比较器读取的是上游命令的成功次数，不一定只有 0/1。`as @a` 可能返回人数，区域操作可能返回受影响方块数。

- `execute ... if ...` 作为纯条件门时，条件成立才返回成功。
- 需要“至少一个目标存在”时，`if entity` 比旧的 `testfor` 更清楚。
- 不依赖具体成功数值来推断容量、伤害或库存；这些状态应显式存入 tag 或 `dummy` 分数。

## 常用起手式

### 1. 每刻根

```text
【循环｜无条件｜保持开启｜延迟0】
/scoreboard players add .clock clock 1
```

后面全部接连锁。每刻根只放最轻的检测，重命令用计时器降频。

### 2. 按钮根

```text
【脉冲｜无条件｜需要红石｜延迟0】
/scoreboard objectives add menu dummy "雪球菜单"
```

后面接连锁，全部 `无条件｜保持开启｜延迟0`。按钮按一次，整条链跑一次。

### 3. 一次性初始化

推荐单独搭一条按钮链：

```text
A1【脉冲｜无条件｜需要红石｜延迟0】
/scoreboard objectives add menu dummy "雪球菜单"

A2【连锁｜无条件｜保持开启｜延迟0】
/scoreboard objectives add clock dummy "全局时钟"

A3【连锁｜无条件｜保持开启｜延迟0】
/scoreboard players add .clock clock 0

A4【连锁｜无条件｜保持开启｜延迟0】
/gamerule commandblockoutput false
```

- A1 用“需要红石”的脉冲方块，按一次按钮完成初始化；A2–A4 接常开无条件连锁。
- 建目标、设置全局初始值、修改游戏规则这类操作不要塞进循环方块。每刻重复执行既浪费，也容易让修改后的全局状态被悄悄重置。
- 需要照顾后来加入的玩家时，运行链里可以保留 `scoreboard players add @a <目标> 0`。`add 0` 只给没有分数的对象补零，不覆盖已有进度；不要改用 `set`。
- 初始化脚本若已执行过，再按一次时 A1 可能失败；后面的“无条件”连锁仍会继续。不要为了让 A1 再次成功而删除已有目标。
- 不要用“脉冲｜保持开启”当一次性初始化。脉冲方块要在“需要红石”时由按钮或压力板触发；做持续运行请用一个独立的循环根。

### 4. 临时标签锁定

先锁定，再改分数/物品，避免后面的命令判断不到：

```text
【循环｜无条件｜保持开启｜延迟0】
/execute as @a[scores={coins=100..},hasitem={item=diamond,quantity=1..}] run tag @s add buying

【连锁｜无条件｜保持开启｜延迟0】
/execute as @a[tag=buying] run scoreboard players remove @s coins 100

【连锁｜无条件｜保持开启｜延迟0】
/execute as @a[tag=buying] run clear @s diamond 0 1

【连锁｜无条件｜保持开启｜延迟0】
/execute as @a[tag=buying] run give @s apple 1

【连锁｜无条件｜保持开启｜延迟0】
/tag @a[tag=buying] remove buying
```

如果先扣分，后面 `scores={coins=100..}` 就不匹配了。标签是纯指令里最可靠的“中间变量”。

## 玩家进出的限制

- **首次进入**：`scoreboard players add @a online 0` 给尚无分数的在线玩家补 0；`@a[scores={online=0}]` 只触发一次；最后把 0 改成 1。这个状态会存档。
- **世界运行中的断开再进**：使用独立目标，按 `add @a ... 0` → 欢迎 0 分玩家 → `reset *` → `set @a ... 1` 的顺序执行，共 4 格。`reset *` 会清理所有持有该目标分数的记录，只能用于这类事件目标，不能套到金币、冷却或档案分数。完整退出世界再打开时没有独立载入信号，必须实机复核首个玩家行为。
- **下线检测**：玩家离开后不能再被选择器选中，也不能对他本人执行命令。每刻记录在线人数并与上一刻比较，可以检测总人数净减少；它不能指出具体是谁离线，同一刻一人进入、一人离开时净差还可能为 0。

## 性能

每刻都跑的东西：

- 不要 `@e` 裸扫；加 `type=`、`r=`、`c=1`。
- 不要每刻 `tellraw @a`；用计时器降到 1 秒/5 秒。
- 不要每刻大范围 `fill`/`clone`；拆成按钮触发。
- 先 `execute if entity`/`if score` 过滤，再执行重命令。
- 用 `tag` 锁一次，避免同一个玩家每刻重复领奖。
- 链越长越贵；超过几十格就拆成多个根，用分数/标签交接。
- 多个系统共用同一条轻量循环根，分别用自己的分数或标签门控；不要为每个 HUD、冷却和提示各开一个 20 Hz 根。

降频模板：

```text
【循环｜无条件｜保持开启｜延迟0】
/scoreboard players add .tick timer 1

【连锁｜无条件｜保持开启｜延迟0】
/execute if score .tick timer matches 20.. run scoreboard players set .tick timer 0

【连锁｜无条件｜保持开启｜延迟0】
/execute if score .tick timer matches 0 run say 每秒一次
```

## 加载与游戏规则

```text
/gamerule commandblocksenabled true
/gamerule commandblockoutput false
/gamerule sendcommandfeedback false
/gamerule maxcommandchainlength 65536
```

- `commandblocksenabled` 为 false 时所有命令方块失效。
- `maxcommandchainlength` 为 0 时连锁不执行；不要设 0。
- `commandblockoutput` 控制命令方块输出；调试时开，正式关。
- `sendcommandfeedback` 控制命令反馈；正式关。
- 远处系统用常加载区：

```text
/tickingarea add 0 0 0 10 10 10 menu
/tickingarea list
```

## 排错顺序

先按三层定位：

1. **有没有触发**：红石源、循环开关、链头类型、箭头方向、区块加载和 `commandblocksenabled`。
2. **有没有解析**：打开 Previous Output，确认命令版本、参数数量、文本 JSON、全角符号和网易是否支持该命令。
3. **有没有选中与落地**：单独运行选择器，检查执行者、位置、维度、分数、tag、背包槽位和后续动作。

仍无法定位时，在链中间插入临时 `say` 或 `tag` 探针，再用二分法删除一半后段。修好后删除探针、恢复提示规则和临时 tag。

1. **上一格输出**：打开命令方块看 Previous Output，先看报错。
2. **箭头**：连锁方块是否指对下一格。
3. **条件**：有条件是不是被上一格失败卡住了；先改无条件试。
4. **红石**：循环根是不是“需要红石”但没供能；连锁是不是被设成了需要红石。
5. **区块**：玩家离开后是否停了；加 `tickingarea`。
6. **游戏规则**：`commandblocksenabled`、`maxcommandchainlength`。
7. **目标不存在**：先跑 `scoreboard objectives list`。
8. **全角符号**：`～`、`，`、`：`、`｜` 都会让命令解析失败。
9. **选择器**：`limit`、`distance`、`nbt`、`team` 在基岩版直接失效。
10. **重复触发**：分数没重置、标签没移除、脉冲根被红石持续供能。

## 输出模板

给用户完整系统时，每格都写成：

```text
B1【循环｜无条件｜保持开启｜延迟0】
/持续运行的命令

B2【连锁｜无条件｜保持开启｜延迟0】
/后续命令
```

最后补一句：

```text
摆放：先单独完成初始化链；B1 循环方块放运行链起点，B2 以后接常开无条件连锁，箭头依次指向下一格。
```
