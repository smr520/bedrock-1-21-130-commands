# 命令方块验收矩阵

这份矩阵用于把“语法看起来对”和“目标客户端已经验证”分开。交付时只报告实际完成的层级；没有实机结果时写明“仅静态检查”。

## 验证层级

| 层级 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 静态语法 | 没有明显的旧 `execute`、Java 参数、全角符号、坏 JSON 和参数数量错误 | 命令在目标客户端一定存在或一定能执行成功 |
| 结构检查 | 方块标注完整、总数匹配、ID 不重复、链的起止关系清楚 | 箭头、红石、区块和游戏规则已经摆对 |
| 单人实机 | 正常路径、失败路径、状态初始化与清理可用 | 多人争用、选择和持久化没有问题 |
| 多人实机 | 同刻点击、近距离玩家和标签锁定正确 | 服务器长期运行没有资源或边界问题 |
| 持久化实机 | 区块卸载、重进、停服与世界重开后仍符合设计 | 所有设备和发行渠道表现一致 |

本 skill 的默认实机目标是**网易中国版 3.10 / BE1.21.130**。国际版测试结果只能证明国际版行为；同一命令在两个渠道都通过后，才能写“国际版兼容且网易通过”。

## 静态检查

每套方案至少检查：

- 所有命令位于代码块或命令方块序列中，说明文字没有被误粘成命令。
- 每格只有一个命令；动作型现代 `execute` 以 `run <命令>` 结束，纯条件型则必须以完整的 `if/unless block|blocks|entity|score` 条件收尾。
- 记分板目标都先创建，内部名使用 ASCII。
- 没有 `/function`、`/schedule`、`/reload`、Java `execute store`、`data get` 或未声明的外部资源。
- 选择器没有 Java-only 的 `limit=`、`distance=`、`sort=`、`nbt=`、`team=`、`predicate=`、`advancements=`；实体查询没有漏掉 `type` 和范围。
- 名称筛选使用 `name=` 或否定式，不把 `predicate=` 当成名字模糊匹配；`tp/teleport` 等别名与主命令语法一致。
- `if/unless score` 的运算符两侧都能解析成单一目标；没有直接放入未限量的 `@a`、`@e`。
- `tp/teleport` 的实体目的地能解析成单一实体；多目标选择器加 `c=1` 或改用 `@p`、`@s`。
- 每个 `as`、`at` 分叉都报告来源数、目标数和执行频率，没有隐藏的乘法扫描。
- JSON 引号、花括号和 `\n` 转义正确；命令语法部分没有全角标点。
- 每个方块标注都写成“类型｜条件｜红石｜延迟”，编号在同一套示例中唯一。
- 开场声明的命令方块总数等于实际带编号的方块数；聊天栏准备命令单独记为 0 格。
- 一次性 `objectives add`、`gamerule`、`tickingarea add` 和大范围 `fill/clone/structure` 没有放进每刻循环。
- 不在网易官方命令表中的 `titleraw`、`damage`、`hud` 等已列出 `/help` 结果；`camera`、`inputpermission`、`dialogue`、`loot`、`place`、`recipe`、`scriptevent` 默认没有进入主链。
- `function`、`schedule`、`reload` 没有被用来替代命令方块链；若用户明确改为函数/附加包方案，则重新定义交付边界。
- 复杂方案已通过 `validate-chain-spec.mjs`，spec 的命令、拓扑、条件、延迟、朝向和纯命令边界一致。

已有 `.mcworld` 作为训练语料或迁移来源时，还要检查：

- 用 `audit-mcworld.py` 只读确认 ZIP 路径安全、`level.dat`、世界名、命令/作弊/命令方块开关和 `db/*.log`；如果只有 `.ldb` 表文件，应保留“当前无法提取命令”的明确状态。
- 报告链式、循环、脉冲三类命令方块数量；单独列出空命令、非空命令、唯一命令、保持开启、条件、延迟和最大命令长度。
- 先导出到私有临时目录，再运行 `validate-commands.mjs --channel netease`；地图中存在命令不能升级成客户端执行成功。
- 扫描玩家名、内部目标名、绝对坐标、网易专用 ID、地图标语和结构名；发布包只保留匿名化模式和重写后的最小示例。
- 原始 `.mcworld`、完整命令导出和审计报告不进入允许公开再分发的仓库，除非作者和素材许可证都明确允许。

## 单人功能测试

| 检查项 | 预期结果 |
| --- | --- |
| 初始化只按一次 | 目标、假玩家和全局值建立；重复按不会清掉玩家进度 |
| 正常成功路径 | 扣费、清物品、发奖励、传送到位等步骤各执行一次 |
| 条件失败路径 | 分数不足、没有物品、分数未建立时不会扣掉另一项资源 |
| 边界数量 | `0`、刚好够、差 1、超过上限、负值和范围端点行为明确 |
| 重复触发 | 按钮长按、红石持续供能或玩家反复进入不会重复领奖 |
| 状态清理 | 临时标签、临时分数、刷屏提示和菜单状态在完成后归零 |
| 撤回与离开 | 撤离区、菜单、冷却和倒地在离开后回到设计状态 |
| 传送目标 | 目标位于触发区外、可安全站立，不会立即再次触发同一机关 |
| 背包状态 | 空背包、刚好数量、多余数量、满背包和同 tick 多次交易均有结果 |
| HUD 共存 | 动作栏、标题、侧边栏同时启用时不会被多个高频链互相覆盖 |

## 多人测试

至少使用两名玩家：

1. 两人都进入按钮三格范围，确认 `@p` 是否可能锁到另一人。
2. 两人同一 tick 点击同一按钮，确认不会共用中间标签或重复结算。
3. 一人交易时另一人移动、换物品或离开，确认操作对象不会改变。
4. 两人同时在撤离区累计，确认进度互不覆盖。
5. 一名玩家死亡、重生或切换维度后，确认临时标签和菜单状态仍按设计处理。
6. 多人同时丢雪球时，确认“落点最近玩家”与真正投掷者不同所导致的限制被明确说明。
7. 同分或配对系统使用两名在线玩家、不同分数、单方离线和双方挤在触发点四组路径测试。
8. 使用多个候选目标时，确认命令不会把来源依次传送到每个匹配目标后才停在同一 tick 的最后位置。
9. 玩家死亡、旁观或切换维度后，确认 `@a`、`@p`、`rm=` 的变化不会产生空目标或跨维度误判。
10. 两名玩家同 tick 进入时，每人只收到一次进服动作；退出重进后再次触发。
11. 一人离开时人数差链能发现净减少；同一 tick 一人进入、一人离开时按设计说明可能净差为 0。
12. 两个网易客户端设备或帧率不同，同 tick 操作、视角确认和动作栏刷新仍符合预期。

共用的固定按钮若允许两个人同时接近，就不能依靠连续 `@p` 完成多步交易。需要先用临时标签锁定操作对象，并在成功或失败路径都清理标签。

## 纯命令 UI 测试

菜单、HUD、商店确认页和其他交互式文本至少检查：

| 检查项 | 预期 |
| --- | --- |
| 当前选择 | 同时有文字/符号和颜色，不只靠颜色 |
| 锁定原因 | 分数不足、背包满、冷却、离线等有明确提示 |
| 取消路径 | 至少一种设备可稳定触发的关闭或返回方式 |
| 终止清理 | 成功、失败、取消都清零菜单编号、选择锁和临时标签 |
| 生命周期 | 死亡、重生、传送、换维度、重进后不会卡在隐藏状态 |
| 输入一致 | 触摸、键盘和手柄都能完成核心操作 |
| 对话重新验证 | 确认前重新检查在线、资源、距离和交易锁 |
| 输出职责 | 长信息用 `tellraw`，短 HUD 用动作栏，关键阶段用标题 |
| 刷新成本 | 状态不变时不按 tick 重发大 JSON |
| 多人冲突 | 两人同 tick 操作不会共用选择者或重复结算 |

详细规则见 [command-ui-playbook.md](command-ui-playbook.md)。

## 多系统组合测试

- 两个系统是否错误共用同一动作栏、同一临时标签或含义不同的同名记分板目标。
- 两个独立冷却是否各自保留目标，只在循环递减处共享根方块。
- 菜单、撤离进度和普通 HUD 同时存在时，屏幕优先级是否明确。
- 两个按钮链是否都清理自己的 `tx_`、`select_`、`menu_` 或 `cb_` 临时标签。
- 配方登记中的目标名、标签、方块预算和多人模式是否与实际命令一致。

## 持久化与部署测试

- 把玩家带离所有命令方块所在区块，再走回；循环链应先加 `tickingarea` 或明确要求玩家靠近。
- 保存并退出世界后重进，确认记分板、标签、菜单状态和冷却没有被错误重置。
- 关闭再开启红石、拉杆和压力板，确认脉冲方块不会持续重复执行。
- 检查 `commandblocksenabled`、`maxcommandchainlength` 和 `commandblockoutput`。
- 检查每条链的方块朝向。有条件方块只读取上一格结果，不读取分数。
- 所有结构名、出生点、传送点、地毯和破坏范围都使用实际地图坐标，并标明待替换项。

## 版本与渠道测试

- 在网易 3.10 / BE1.21.130 上先用 `/help <命令>` 验证不在官方命令表中的命令，再执行最小命令测试。
- 在 `titleraw`、`damage`、`hud`、`playanimation`、`camerashake`、`replaceitem ... keep` 等语料常见能力上记录 `official`、`client-confirmed` 或 `corpus-observed`，不能混写。
- 新实体、新物品、新效果和新附魔 ID 同时在网易客户端补全、召唤/给予/施加并记录实际结果。
- 目标为国际版时，再单独验证国际版 1.21.130；不要把网易通过的结果自动写成国际版通过。
- 网易专用实体、粒子、NPC 和伙伴实体只在其渠道清单中验证，不能自动转换成 `minecraft:` 命名空间。
- 纯原版通用语法可以在未确认渠道前先完成；渠道专用 ID 不能未经测试就混入正式命令。
- 旧版客户端不支持 1.21.130 新 ID；交付时写明最低版本。

## 能力边界测试

- 自定义生命分数不会自动同步自然摔落、近战、饥饿或药水伤害。
- 纯命令方块不能可靠读取实体真实生命值，也不能在没有显式伤害事件时维护精确 BOSS 血量。
- `scoreboard` 冷却只表示在线且链运行期间的累计刻数，不等于现实自然日。
- `reset *` 配合专用事件目标可以识别世界运行期间的断开再进；完整世界退出再打开没有独立载入信号，必须实机确认首个玩家行为。该状态不能用来保留长期玩家档案。
- 玩家真正离线后不能再被选择器选中。人数差只能检测在线人数净减少，不能指出具体是谁离线，且同一 tick 进出可能抵消。
- `@p`、雪球落点和最近实体是近似选择，不应称为精确投掷归属或精确命中。
- 命令方块的 `@s` 默认是命令方块自身；只有通过 `execute as` 后才可能代表玩家。纯红石按钮没有“按压者”选择器。
- `@initiator` 只存在于 NPC 对话命令上下文，不能替代普通命令方块的按钮归属判断。

## 验收报告

交付方案末尾可附：

```text
命令方块总数：
静态检查：通过 / 未通过
目标客户端：
已实机验证：
未验证项：
已知差异：
旧语法或语料来源：
```

只有实际在目标客户端完成了对应路径，才能把该项写成“已通过”。
