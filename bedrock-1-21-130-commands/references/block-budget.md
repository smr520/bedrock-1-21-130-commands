# 减少命令方块：预算与压缩规则

目标是在玩法不变或只牺牲装饰效果时，尽量减少命令方块数量。一个命令方块仍然只能执行一条命令，不能把多条命令用换行、分号或 `execute` 拼在同一个方格里。

## 执行分叉预算

命令方块数量不能单独代表性能。`as`、`at` 每匹配一个目标就会复制一次后续执行，连续分叉的实例数按乘法增长：

```text
每次触发的实例数 ≈ 来源匹配数 × 目标匹配数 × 后续分叉数
每秒实例数 ≈ 每次触发的实例数 × 每秒触发次数
```

例如 `as @a` 后接 `at @a`，在 20 名玩家在线时不是执行 2 条命令，而是约 400 个执行实例。即使只占 1 个命令方块，也可能比一条简单循环链更重。

交付压缩方案时要同时报告：

- 命令方块数。
- 分叉子命令的目标数量或选择器范围。
- 每次触发的最大实例数。
- 循环触发间隔或按钮触发频率。
- 用什么 `tag=`、`r=`、`c=` 或状态条件限制集合。

同一逻辑中存在“比较两个集合”的需求时，优先用 `as → at @s → at 对比集合` 保存来源和目标上下文；来源通常加 `c=1` 或专用标签，目标集合必须控制为实际需要的大小。不要用 `@e` 裸扫来省一个计数参数。

多个系统同时安装时，先读 [shared-core.md](shared-core.md)：首次进入、统一 HUD、独立冷却递减和多人交易锁可以按模块复用，避免每个玩法各建一套启动和显示链。

普通 HUD、撤离和菜单同时需要动作栏时，使用 [hud-arbiter.md](../examples/hud-arbiter.md) 的三格优先级链替换各系统自己的循环输出，避免后执行的提示覆盖前一条。

## 先报预算

给用户方案时写明：

```text
准备：1 条聊天栏命令（0 个命令方块）
C1–C3：购买链，3 个命令方块
合计：6 个命令方块
```

如果用户要求连初始化也必须在方块里完成，再加一个“脉冲｜需要红石”的根和一个按钮。不要为了统一格式，把聊天栏一次的准备工作浪费成循环方块。

## 第一优先级：合并检测与动作

动作型 `execute` 应把 `/run <命令>` 放在末尾；只判断成功/失败时，完整条件可以直接结束命令，例如 `/execute if entity @a[tag=ready]`。如果先给目标打临时标签、再用标签执行动作，还会多出标签清理：

```text
浪费：至少 3 个方块，还要处理重复触发
/execute as @a[scores={coins=100..}] run tag @s rich
/execute as @a[tag=rich] at @s run titleraw @s actionbar {"rawtext":[{"text":"金币足够"}]}
/tag @a[tag=rich] remove rich

精简：1 个方块
/execute as @a[scores={coins=100..}] run title @s actionbar 金币足够
```

常用条件直接放进选择器：

| 条件 | 直接写进选择器 |
| --- | --- |
| 分数 | `scores={coins=100..}` |
| 背包物品 | `hasitem={item=diamond,quantity=1..}` |
| 距离 | `r=3` / `rm=3` |
| 抬头/低头 | `rx=-88` / `rxm=88` |
| 实体类型 | `type=zombie`、`type=!player` |
| 最近一个 | `c=1` |

选择器能用时，先不用 `tag`、`if score`、`if entity` 各占一格。

## 第二优先级：用延迟循环根代替计时链

每 5 秒执行一次的动作直接放在循环方块里，把延迟设为 `100`：

```text
1【循环｜无条件｜保持开启｜延迟100】
/title @a actionbar §a5 秒到了
```

这通常比“每刻给时钟加 1、判断、归零、显示”少 3–4 个方块。需要“首个玩家秒级欢迎”时，另建一条延迟 0 的轻量循环链；不要为了省一个公告方块，让所有玩家等待。

延迟只决定该命令方块多久执行一次，不会把多个命令合并。需要依赖同一 tick 顺序的操作仍应放在一条连锁里。

## 第三优先级：精简显示

菜单显示默认采用一个动作栏块：

```text
/execute as @a[scores={menu=1..6}] run titleraw @s actionbar {"rawtext":[{"text":"§e雪球菜单，当前 "},{"score":{"name":"@s","objective":"menu"}},{"text":" / 6\n1 主城  2 返回  3 商店\n4 设置点  5 奖励  6 关闭"}]}
```

选项高亮通常要每个选项一格。若用户优先追求最少方块，使用“总菜单 + 当前编号”，可以少 `选项数-1` 格。

每个选项真正执行的动作仍要各占一格；例如传送、给药、切换模式无法由显示块兼任。

语料里还有一种“少格大命令”写法：把多层 `translate`、多个 `selector` 和连续几十个 `positioned` 塞进一条 `execute`。它能减少方块数，但会提高解析成本，难以调试，也更接近 32,500 字符上限。默认只在确实需要节省空间时使用，并在交付中同时报告预估单条命令长度与每刻扫描范围。

语料中常见的动态命令方块（用 `setblock` 改写另一格的命令文本）也不是默认方案。它能减少静态动作格，但会引入字符串转义、坐标依赖、重进恢复和自修改链排查问题。除非玩法确实需要数据驱动命令，否则先做静态方块链。

## 第四优先级：去掉非核心装饰

以下命令会带来更多方块，但通常不决定玩法：

- 成功音效
- 成功提示
- 粒子特效
- 关闭菜单后的额外提示
- 仅用于静态检查的测试按钮

默认精简版先省掉这些；用户确认玩法后再按需逐条加回。

## 标签与交易安全

`tag` 适合固定一次多步交易中的同一个玩家，但会多出“打标签”和“清理标签”两格：

```text
1 条件选择并打标签
2 扣分
3 清物品
4 发物品
5 清理标签
```

单人按钮区的精简版可以连续使用同一个 `@p[r=3]`：

```text
1 扣分
2 清物品
3 发物品
```

后两格使用“有条件连锁”；前格成功后整条链继续。多人共用同一按钮时，`@p` 可能选到另一个人，应该改用标签方案。不要为了少两格牺牲多人服务器里的交易正确性。

## 状态初始化

- `scoreboard players add @a target 0` 只补缺少分数的在线玩家，适合持续运行链。
- 后续 `scoreboard players add/remove` 通常也会创建缺失条目；如果查询或购买门槛必须立即把新玩家视为 0，就保留一格补零。
- 建目标和设置全局初值只做一次，优先在聊天栏执行。
- 不要每刻 `set` 玩家分数，否则会覆盖真实进度。

## 最少化检查清单

1. 是否能用 `as/at/if/unless` 把检测和动作合成一条？
2. 是否已经用 `scores`、`hasitem`、`rxm` 等选择器条件？
3. 是否把固定间隔误做成了每刻时钟链？
4. 是否把一次性初始化放进了循环？
5. 菜单是否可以先共用一个显示方块？
6. 音效、提示、粒子和测试按钮能否推迟？
7. 删除的方块是否影响交易原子性、多人选择或状态清理？
8. 交付是否标出了方块总数和每一项的取舍？
9. 是否为了减少方块把过多条件塞进单条命令，导致性能和维护成本上升？
